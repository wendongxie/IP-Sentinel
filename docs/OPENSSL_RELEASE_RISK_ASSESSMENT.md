## CVE-2026-107493 的适用性

**官方严重度为低。** 触发需要调用方将已有的非空指针形式的 `X509_INFO` 栈传给受影响的 PEM 解析 API，解析或追加随后失败，调用方又读取或释放仍保存悬空指针的栈。异常 PEM 可以造成解析失败，但无法自行决定调用方传入的参数。潜在后果是应用崩溃或内存破坏。OpenSSL 公告明确指出，内部调用者（包括 TLS 的 CA 加载路径）传入 NULL，公告所述的栈复用条件在该路径不成立。

**静态证据。** 应用的 `ip_sentinel/network.py` 创建 Python 默认 TLS 上下文，再加载本地 certifi CA 文件并传给 HTTPX。出口探测、风险名单和机器人通知共享该客户端。网络输入包括 TLS 对端证书、代理端点和 HTTP 响应。Windows 信任库、本地 certifi 文件及环境配置指定的信任材料属于本地输入。应用源码未发现直接调用受影响 API、将网络响应当作 PEM 读入、或使用 cryptography。旧包的 PyInstaller 模块交叉引用含 httpx、httpcore、certifi 和 h2，未见 cryptography，原生文件盘点也未见其 `_rust` 扩展。h2 是 HTTP/2 组件。旧包含 Qt 的 OpenSSL TLS 插件，应用的 HTTPX 请求路径并未调用 Qt TLS，仍须把插件的动态解析与其他原生间接调用作为独立检查项。

**边界与防护。** 正常 TLS 证书和主机名校验可降低不受信对端风险。它不修复 OpenSSL 内存错误，也不能证明所有解析都发生在身份验证之后。PE 静态导入和普通连接测试都无法排除动态解析、配置变化或未覆盖原生路径。针对当前已知调用，应用暴露评为低，结论不构成不可利用证明。

**原生与动态证据。** 检查旧包 DLL/PYD 的普通和延迟 PE 导入。`_ssl.pyd` 导入 libssl 和 libcrypto，`_hashlib.pyd` 导入 libcrypto，未见这两个模块直接导入 PEM 栈解析函数。QtNetwork 绑定及 TLS 插件存在 DTLS 相关 Qt 符号，证明能力随旧包分发。静态符号不足以判断应用是否调用，也无法覆盖 Qt 插件运行时解析的 OpenSSL 符号。另在隔离的 Astral 3.5.9 解释器下，用项目客户端和 HTTPX 0.28.1 直连 Python.org，返回 HTTP/1.1 200。外部主机名不匹配站点的请求出现连接错误，诊断未得到明确的证书拒绝原因，故该项未验证。15 项现有自动化测试全部通过，其中 TLS 测试检查主机名验证开启及 `CERT_REQUIRED`。这些测试未验证漏洞触发条件、实际代理链或最终冻结合集。

从已校验的 QtBase 6.12.0 源码查看 `src/plugins/tls/openssl/` 的 C++ 实现和头文件，未发现 `PEM_X509_INFO` 字样，发现插件解析并可调用 DTLS 监听 API。这支持对 Qt TLS 插件单独管理安全版本的必要性，不代表应用启动了 DTLS 或排除了间接的 PEM 调用。

## 3.5.9 剩余披露

| 公告 | 官方等级 | 应用暴露判断及依据 |
| --- | --- | --- |
| CVE-2026-107493 | 低 | 低。默认 CA 加载路径不满足栈复用条件，其他原生调用仍有证据边界。 |
| CVE-2026-124709 | 低 | 低。涉及 QUIC 服务端拒绝流后的内存保留。应用仅使用 HTTP 客户端及本机 Qt 单实例 IPC，没有发现 QUIC 服务端。 |
| CVE-2026-88822 | 低 | 低。涉及 QUIC 自动对端检测时的未初始化内存。现有 HTTPX 路径使用 TCP 上的 HTTP，未发现 QUIC 配置。 |
| CVE-2026-95691 | 低 | 低。涉及 QUIC 客户端处理重传。未发现 HTTP/3 或 QUIC 客户端调用。 |
| CVE-2026-35190 | 低 | 低。需要服务端显式设置 Suite B 证书标记并处理 TLS 1.3 握手，应用未发现此服务端路径。 |
| CVE-2026-88823 | 低 | 低。需要应用用 AES-GCM-SIV 分段传入 AAD，且含零长度片段。未发现该加密业务。 |
| CVE-2026-95692 | 低 | 低。需要应用使用非标准长度 IV 初始化 AES-GCM-SIV。未发现此用途。 |
| CVE-2026-107496 | 低 | 低。需要应用对攻击方可控的收件人证书执行 CMS 加密。未发现 CMS 加密功能。 |
| CVE-2026-84782 | 高 | 3.5.8 旧包仍在受影响版本范围，3.5.9 达到官方高危修复边界。 |

本次未找到上述 3.5.9 剩余披露在现有应用路径中构成中风险或高风险的证据。按工程决策，若在完成新载荷原生检查前例外接受 3.5.9，未覆盖路径与后续维护属于中等不确定性。该项不替代官方 CVE 严重度，也不改变发布门槛。

## 发布选择

| 路线 | 安全性 | 开发成本 | 长期维护 | 发布速度 | 合规影响 |
| --- | --- | --- | --- | --- | --- |
| A 等待可信发行方 | 满足原门槛后仍需实测并扫描载荷 | 较低 | 由上游维护运行时，项目跟踪发布 | 受发行时间限制 | 仍须完成 Qt 交付，按实际运行时更新声明 |
| B 自建 CPython/OpenSSL | 可在固定官方源码并完成全部验证后达到门槛 | 高 | 自行维护工具链、补丁和升级 | 取决于工具链就绪与验证进度 | 仍须完成 Qt 交付，另需保留自建运行时许可与补丁信息 |
| C 申请接受 3.5.9 | 已修复旧包高危项，保留表中已知风险 | 初期较低，仍需完整重建和验证 | 需约定例外期限和退出条件 | 可能较快，但受用户批准和 Qt 门槛制约 | 用户同意安全例外不会改变 LGPL 义务 |

推荐 A。B 可在取得明确发布期限后并行准备工具链与可重现性验证。C 仅适合明确期限约束下的书面例外，且应先验证最终归档的原生载荷、HTTPS 与代理路径，并在修复运行时可验证后重建和替换发行物。本轮未接受例外。
